# 钓鱼系统 V2 重做实施基准

> 状态：V2 第一阶段代码已在独立分支制作；尚未合并、尚未执行 Supabase SQL，也尚未进行线上实机验收。

## 当前实现内容与迁移顺序

本阶段代码已经包含：
- 36 种鱼类：原有 10 种 + 22 种新增常规鱼 + 4 种隐藏鱼。
- 3 个钓点：晴岚湖、芦苇湿地、深水湾。
- 6 种共享天气：晴、阴、雨、雾、雷雨、大风；按服务器四小时天气时段生成并保存未来预报。
- 鱼类条件：钓点、天气、前序天气、北京时间时段、前置鱼种发现。
- 天气影响鱼种出现条件/权重，并可将 0–10 个百分点从小型鱼概率转移到大型鱼概率。
- 收线评分由服务器时钟和每次会话随机相位决定；客户端不提交评分或成功标记。
- V2 使用独立的 fishing_start_cast_v2 / fishing_hook_cast_v2 / fishing_finish_reel_v2 RPC；旧 V1 RPC 在数据库准备阶段暂时保留，确保旧前端仍能运行。待新版前端部署并通过实测后，再执行单独的激活迁移停用旧 V1 抛竿入口和旧鱼饵商店商品。
- 具体尺寸由服务器生成；图鉴同时展示个人最佳尺寸与全服历史最大尺寸。纪录奖励基准独立保存，避免多次小幅进步重置奖励门槛。首次发现 ×3、纪录刷新 ×2、普通重复 ×0.2；收线附加积分 0/2/4/5%，最后向下取整。
- 普通鱼饵继续消耗树果制作；特殊鱼饵可消耗三种稀有材料制作，也可由成就/活动发放。
- 旧四种无限积分鱼饵商品下架，但不删除兑换历史、不扣除玩家已有积分/鱼饵。商店保留 V2 的卡牌/道具/网站代币奖励管理能力；新的兑换商品与价格暂不盲目预设，需先核对现有网站代币和卡牌经济，避免把旧刷分问题转移到新商品。
- 隐藏鱼未发现前不通过鱼类目录接口暴露名字；图鉴只显示隐藏鱼种数量和线索提示。

当前简化项：FFXIV 风格的天气/时段/前置鱼种条件已接入；完整的“活饵消耗链”和短时间内连续捕获组合触发的“直觉”机制暂不启用，留待后续阶段，避免第一批数据库改动过大。

### Supabase SQL 执行顺序

以下文件按顺序执行。已执行过的旧迁移无需重复手动执行；新增 V2 安装文件只需执行一次：
1. supabase/fishing-system-v1.sql
2. supabase/fishing-server-authoritative-v1.sql
3. supabase/fishing-achievements-shop-v1.sql
4. supabase/item-workshop-mail-v1.sql（提供现有道具目录；若已执行则跳过）
5. supabase/fishing-shop-v2.sql（若尚未执行；启用钓鱼商店的跨系统奖励类型）
6. supabase/fishing-overhaul-v2-preflight.sql（只读预检，确认旧数据与依赖）
7. **只需执行一次** supabase/fishing-overhaul-v2-install.sql（将目录、天气、钓点、36 种鱼、隐藏鱼、特殊鱼饵和 V2 RPC 放在同一个数据库事务中；任何一步失败都会整体回滚，旧系统保持不变）
8. supabase/fishing-overhaul-v2-verify.sql（只读验收，不修改数据）
9. 合并 PR 并等待 Pages 部署；先验证新版钓鱼页面和非钓鱼模块。
10. supabase/fishing-overhaul-v2-activate.sql（仅在新版前端实测通过后执行：停用旧抛竿入口和旧积分鱼饵商品）
11. supabase/fishing-overhaul-v2-activate-verify.sql（只读确认旧入口已关闭、V2 RPC 正常）

**注意：** 两份 V2 核心迁移先部署数据库兼容层，不会立即关闭旧入口；新版前端部署并实测通过后，再单独执行最终激活迁移。这样避免出现“旧前端先失效”或“新前端找不到数据库函数”的切换空窗。GitHub 提交不会自动修改 Supabase 数据库。

### 本阶段明确不修改

- auth.js、player-center.js、头像框、登录/会话恢复。
- 卡组构筑、卡牌收藏、抽卡 RPC、对战系统。
- profiles、player_stats、card_inventory 表结构。
- 全站导航逻辑；index.html 仅变更钓鱼脚本缓存版本号。


## 目标与不可破坏边界

将钓鱼从单纯消耗鱼饵、重复收线刷积分，升级为资源规划、鱼种收集、尺寸挑战、天气窗口、隐藏鱼与长期图鉴玩法。

**最高优先级：不得破坏现有非钓鱼模块。**
- 不修改登录认证流程、会话恢复、玩家中心初始化、头像框、卡组构筑、卡牌收藏、抽卡、对战或其他无关 RPC。
- 不修改 profiles、auth.users、player_stats、card_inventory 的结构；只允许在专用钓鱼 RPC 内按现有接口读取/扣除树果。
- 前端逻辑限定在 fishing.js（或新独立 fishing-v2.js）和 #fishing-view 范围内。不得重构全局导航或公共启动器。
- 数据库采用新增、可重复执行的专用 migration；优先新增钓鱼字段/表/函数，不重写基础建表迁移。
- 保留现有玩家积分、树果、鱼饵、鱼图鉴、钓获流水、成就记录和兑换记录。停用旧鱼饵商品而非删除历史商品或兑换记录。
- 每个阶段单独 PR；CI、静态检查和差异审查通过后才合并。先测试账号验收，后实机玩家验收。任一阶段异常立即停止后续部署并回滚该阶段。
- 不把“代码已提交”“Actions 通过”“Pages 部署完成”“SQL 已执行”“线上验收通过”混为一谈。

## 已确认的经济与奖励规则

### 鱼饵
- 小型混合饵：任意 1 个树果。
- 中型混合饵：2 种不同树果。
- 大型混合饵：3 种不同树果。
- 成分不明的混合饵：稀有材料制作，或成就/活动奖励，两种途径并存。
- 每次抛竿消耗 1 个鱼饵；失败不返还。
- 普通鱼饵不再通过积分商店无限购买。特殊鱼饵也不直接无限售卖。
- 树果不能只依赖钓鱼获得；必须盘点并利用网站其他玩法现有来源，避免形成新的封闭资源循环。

### 普通收获时的尺寸基础概率
| 鱼饵 | 小型 | 中型 | 大型 |
|---|---:|---:|---:|
| 小型混合饵 | 70% | 25% | 5% |
| 中型混合饵 | 40% | 45% | 15% |
| 大型混合饵 | 20% | 50% | 30% |
| 特殊混合饵 | 10% | 45% | 45% |

### 收线评分
- 0–59：鱼逃走。
- 60–74：普通收获。
- 75–89：良好收获。
- 90–97：优秀收获。
- 98–100：完美收获。
- 收线表现主要改变尺寸概率；暂定积分附加奖励为普通 0%、良好 2%、优秀 4%、完美 5%。
- 服务器必须决定有效评分/结果；客户端不能自报成功与分数。需要设计可抵抗客户端篡改的挑战/时序机制，不能仅以客户端动画或自报时间作为可信证据。
- 指针起始位置、方向/相位应随机化；不能保留固定、可预测的节奏。

### 尺寸
- 每种鱼有独立的小、中、大尺寸区间，生成具体尺寸而非只保存等级。
- 玩家图鉴保存每种鱼的个人最佳尺寸；纪录提升门槛为 max(1cm, 旧纪录的 5%)。
- 新尺寸分布必须与鱼饵基础概率和收线等级一致；概率转移后每行总和必须为 100%，不得出现负概率。

### 积分
- 不设每日积分上限。
- 普通重复钓获：基础积分 20%。
- 首次发现鱼种：基础积分 ×3。
- 刷新个人尺寸纪录：基础积分 ×2。
- 首次发现与纪录奖励不叠加，首次发现优先。
- 收线附加积分倍率只作小幅加成，不与收藏倍率无上限叠乘；实施时必须定义取整规则与奖励顺序。
- 基础积分暂按已确认表格：红鱼 10/15/25；糙鳞鲫鱼 15/25/40；风雅镜鱼 20/35/55；七彩鳟鱼 35/55/85；史郎鲤鱼 50/80/120；稀宝鳟鱼 70/110/170；美味镜鱼 100/160/240；无双鲫鱼 140/220/330；市谷的鱼王 350/600/900；市谷的鱼王之王 600/1000/1500（小/中/大）。
- 新鱼类需在完整鱼种目录中另行平衡，不能照搬鱼王高额奖励。

## 天气、时段与隐藏鱼：新增设计

借鉴 FFXIV 的“鱼种条件组合”深度，但不复制其名称、美术或具体鱼类：
- 天气影响鱼种出现权重、尺寸分布，少数天气能开启限定鱼种。
- 天气使用服务器权威时间与天气状态；前端只展示当前天气和预报，不能决定结算。
- 鱼类条件可组合：栖息水域/钓点、鱼饵、当前天气、前序天气转变、时段、前置鱼种/活饵链、直觉/诱鱼状态。
- 普通鱼在多数天气均可钓，天气主要改变倾向；只有少量稀有鱼使用天气/时段窗口，避免玩家上线时完全无事可做。
- 隐藏鱼在未发现前以剪影/问号显示，不暴露完整名称和条件；发现后加入图鉴。
- 天气预报应能让玩家规划，而不是纯随机瞬间切换；每种天气的持续时间与切换规则固定且服务器可验证。
- 参考 FFXIV 的天气窗口、前序天气转变、活饵（Mooch）和直觉条件，但将复杂度缩放到本项目适合的体量。

### 建议的首发规模
- 从现有 10 种扩展为约 30 种常规/区域鱼类，另加 4–6 种隐藏或传说鱼（总量约 34–36）。
- 至少 3 个有区别的钓点/栖息水域；若现有页面布局不适合，先将其作为钓点筛选，不改全站导航。
- 首发天气建议：晴、阴、多云、雨、雾、雷雨；季节性天气可后续加入。
- 设计普通鱼、天气偏好鱼、天气窗口鱼、活饵链鱼、直觉/成就解锁鱼等层级。
- 天气和隐藏鱼内容应逐步解锁；不要让稀有鱼完全依赖极低概率盲刷。

## 参考 FFXIV 的机制（本项目化简实现）
1. 天气与时段窗口：某些鱼仅在条件组合满足时出现。
2. 前序天气转变：例如“阴转雨”而不只是当前下雨。
3. 活饵链：先钓到指定小鱼，可选择消耗该鱼获/活饵机会，尝试引出更大型目标。
4. 直觉/鱼讯：短时间内捕获指定鱼种组合后，解锁稀有鱼的出现资格。
5. 大物纪录：稀有鱼和大尺寸鱼作为图鉴收藏目标，而非仅提供海量积分。

## 当前仓库审计发现（实施前必须处理）
- 当前目录只有 10 条鱼；基础积分与鱼王仍保留 4500–5500 的旧值。
- fishing_start_cast 当前把所有鱼饵尺寸概率硬编码为 70/25/5，没有使用已确认的各鱼饵尺寸表。
- 当前 small/large 的 size_cm 为空，medium 多数使用固定尺寸；尚未实现连续尺寸范围。
- fishing_finish_reel 计算 action_score，但只用固定绿色区间判断成功；分数没有影响尺寸或积分。
- 当前鱼种只按 bait_id 分池和 appearance_weight 抽取；没有天气、时段、钓点、前序天气、隐藏条件或活饵链。
- 当前 fishing_fish_catalog 结构没有天气/栖息地/稀有度/隐藏条件字段；需用新增扩展表或专用 JSON 配置，避免大规模破坏旧表。
- 当前鱼饵商店商品由 fishing-achievements-shop-v1.sql 初始化；需要新增迁移停用旧鱼饵商品，并设计新的非鱼饵兑换品，保留历史兑换。
- 当前前端 fishing.js 独立运行，页面挂载在 #fishing-view，样式大多限定在 #fishing-view；这是隔离改造的基础。
- index.html 仍负责全局页面/导航和脚本引用；除增加或切换钓鱼专属脚本引用/版本外，不应修改其余全局代码。
- auth.js 是公共登录启动路径；本项目钓鱼重做原则上不得修改 auth.js。

## 实施阶段与验收门槛

### 阶段 0：基线与隔离
- 固定当前 main 基线；独立分支开发。
- 建立非钓鱼模块冒烟检查清单：注册/登录/会话恢复、玩家中心加载、头像框保存/展示、卡组构筑、卡牌收藏、抽卡大厅加载、对战相关页面入口。
- 确认页面脚本无全局变量/事件覆盖冲突；钓鱼初始化失败不得阻断主应用启动。
- 不执行任何生产数据库写入。

### 阶段 1：数据库兼容层
- 新增 migration：扩展天气、钓点、鱼类条件、隐藏鱼、尺寸区间、随机种子/会话快照和新奖励字段。
- 保持现有 RPC 签名兼容或提供新版本 RPC；旧 RPC 在新端到端验收前不撤销。
- 新旧规则并存期间，生产钓鱼入口不得切换到未迁移数据库的新版 RPC。
- 为迁移提供只读预检、执行后验证 SQL、备份/回滚说明。
- 所有玩家奖励结算保持事务与 request_id 幂等。

### 阶段 2：资源与鱼饵
- 普通鱼饵改为树果制作；特殊鱼饵支持材料配方与成就/活动奖励。
- 商店停用旧鱼饵兑换品，不删除兑换历史。
- 确保树果至少有钓鱼之外的获取路径。
- 对库存扣除、配方验证、重复请求和并发进行测试。

### 阶段 3：鱼类、尺寸、天气与隐藏鱼
- 首发 30 种左右常规鱼 + 4–6 种隐藏/传说鱼。
- 建立 3 个以上有玩法区别的钓点/栖息地。
- 加入当前天气、预报、天气转变、时段窗口、鱼种偏好、隐藏条件。
- 加入活饵链/直觉机制，先从少量稀有鱼启用。
- 所有概率和尺寸由服务器结算，配置必须校验总概率。

### 阶段 4：收线与奖励
- 让收线表现主要影响尺寸分布，积分只给小幅附加奖励。
- 首次发现、尺寸纪录、重复捕获采用确定的互斥奖励顺序。
- 纪录与图鉴更新在同一事务中完成。
- 验证异常请求、重放、断线、重复点击不会重复奖励。

### 阶段 5：前端钓鱼体验
- 仅改 fishing 专属脚本和 #fishing-view 样式。
- 显示当前天气、未来预报、钓点、鱼饵建议、隐藏鱼剪影、图鉴条件线索。
- 钓鱼中断/网络错误应明确恢复状态，避免重复扣鱼饵。
- 保留现有页面入口与导航结构。

### 阶段 6：商店、成就与图鉴
- 新增鱼种收集、天气挑战、尺寸纪录、活饵链、隐藏鱼发现成就。
- 商店改为收藏、称号、卡牌/网站奖励等；不再卖可无限回流刷分的普通鱼饵。
- 奖励与库存发放事务化、幂等。

### 阶段 7：测试与上线
- SQL 静态检查、函数权限审查、前端语法检查、差异范围审查。
- 测试账号执行完整流程：制作、抛竿、收线失败/成功、天气限定鱼、隐藏鱼、纪录、重复请求、断线恢复、商店兑换。
- 对非钓鱼模块执行冒烟测试。
- PR 合并后检查 GitHub Actions 和 Pages 部署状态。
- 用户执行 Supabase migration 后，再做线上数据库验收。
- 未完成实机测试前，不宣称钓鱼系统重做上线成功。
